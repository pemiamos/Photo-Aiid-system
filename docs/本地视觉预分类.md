# 本地视觉预分类（v3.4 · 可选功能）

用**本地小模型**给照片做一层便宜的粗分类，把「每张都调 LLM」改成「先本地分，只有拿不准的才调 LLM」。

- 模型：CLIP ViT-B/32（int8 ONNX，85MB）+ YuNet 人脸检测（227KB）
- 硬件：纯 CPU，**不占显存**、不装 torch、不联网（模型下完即离线）
- 速度：**约 112ms/张**（含解码），465 张全库 52 秒
- 收益：低置信只占 **15%**

功能入口：`http://localhost:8000/fast`（或 App 顶栏「AI 预分类」）

---

## 1. 为什么需要它

原来的链路是「每张照片 → 一次云端视觉 LLM」。以 `glm-4v-flash` 并发 2 估算：

| 规模 | 原方案（LLM） | 本功能（本地预分类） |
|---|---|---|
| 465 张 | ≈ 15 分钟 | **52 秒**（仅索引，见 4.1 的完整口径） |
| 1 万张 | ≈ 5 小时 | **约 19 分钟**（仅索引） |

而且预分类会给出**置信度**，人工只需复核低置信那 15%，不必从头看全库。

## 2. 安装

```bash
pip install -r backend/requirements-fast.txt   # onnxruntime / opencv / tokenizers（约 60MB）
python scripts/download-fast-models.py         # 拉模型到 backend/models/（约 148MB，不入 git）
```

模型来源（HuggingFace）：

| 文件 | 用途 | 大小 |
|---|---|---|
| `vision_model_quantized.onnx` | 图像 → 512 维向量 | 85MB |
| `text_model_quantized.onnx` | 类别文本 → 512 维向量 | 62MB |
| `tokenizer.json` | CLIP 分词器 | 2.1MB |
| `face_detection_yunet.onnx` | 人脸检测 | 227KB |

下载脚本支持断点续传（HF 在国内经常断在 80%），重跑会从断点继续。
`--source hf` 可切官方源；`--check` 只检查不下载。

**不装也能用**：`main.py` 对 `fastindex` 做了软导入，缺依赖时整块功能跳过，
其余接口照常工作，只是「AI 预分类」入口不出现。

## 3. 使用

打开 `http://localhost:8000/fast`：

1. 首次点「开始建索引」，选中的文件夹会被扫描并向量化（可看进度 / ETA）
2. 主视图按类别筛选；左侧「待人工复核」筛出低置信项
3. 单击卡片多选 → 底部操作条：
   - **确认无误** → 标 `ok`
   - **标为重复** → 标 `dup`
   - **提交 LLM 复核** → 按路径补齐 `photos` 记录后走原有 `analyzer.analyze_batch`
4. 左侧「重复 / 近似」进入分组视图：每组默认保留第一张，一键把其余标为 `dup`
5. 双击卡片看大图 + **以图搜图**（10ms）
6. 右上角滑块调预览大小（140~440px，记忆到 localStorage）

打标结果存在 `backend/fastvec.db` 的 `vec.flag` 字段（`ok` / `dup` / `llm` / 空）。

## 4. 实测数据

### 4.1 耗时分解（重要：不要只看索引时间）

「万张 19 分钟」只是**索引**这一段。完整的端到端还要算 LLM 复核，而复核是串行的：

| 阶段 | 465 张 | 1 万张 | 说明 |
|---|---|---|---|
| 本地索引 | **52 秒** | **约 19 分钟** | 112ms/张，纯 CPU |
| LLM 复核 | 约 2.4 分钟 | 约 50 分钟 | 仅低置信 15%，glm-4v-flash 并发 2 × 4s/张 |
| **合计** | **约 4 分钟** | **约 70 分钟** | |
| 原链路（全部走 LLM） | 约 15 分钟 | 约 5 小时 | |

**所以真实收益是 3 倍左右，不是 10 倍。** 10 倍只适用于「只建索引、不复核」的场景。

而且降低 LLM 调用量**不是自动的**：本功能给出低置信标记，需要你在界面上选中后点「提交 LLM 复核」。
不做这一步就完全不调 LLM（纯本地分类），做了才产生那 15% 的调用。

### 4.2 两个准确率不是一回事

| 指标 | 数值 | 含义 | 口径 |
|---|---|---|---|
| 分类 top-1 | **87%** | 12 类粗分类的第一名对不对 | 30 张人工标注（D5300 实拍），逐张看图判定 |
| 中文检索 | **85%** | 与人工英译基准的 top-10 重合率 | 10 条固定中文查询 vs 对应英文查询，**不等于检索相关性准确率** |

84 张高置信误判没有单独评估——样本只覆盖了 30 张、12 个类别，不足以支撑更细的分层结论。

复现方式：`python scripts/bench-fast-classify.py <你的照片目录>`（见第 10 节）。样本与标注在本地，不入库。

## 5. 能力边界（务必先读）

**可靠**
- 12 个粗类别的分类（87%）
- 以图搜图（图像嵌入间有真实结构，同主体会聚在一起）
- 重复 / 近重复检测（余弦 ≥0.96，改扩展名、另存、轻微裁切都能抓）
- **中文语义检索**（经内置词典转英文后，与英文基准的 top10 重合 85%）

**不可靠**
- 词典未收录的词。CLIP 文本塔是英文训练的，纯中文查询与英文基准的 top10 重合只有
  **1%**（不是"完全不懂"——中英向量余弦有 0.88，但图文相似度的类间差异只有 0.02，
  而中英向量偏差 0.12，偏差比信号大 6 倍，排序必然被打乱）。
  词典只覆盖摄影场景常见词，生僻表述会退回原文并按原文检索，结果可能不准。
- **细粒度识别**（鸟种、花科）。整图 224×224 输入，小区块像素不够；需要先做主体检测再裁。

**已知误判模式**
- 纹理类：海边礁石被判「哺乳动物」（岩石纹理像毛发）。置信度 0.47 < 0.5，会落进低置信桶。
- 人+大背景：人站在大石碑前会被 CLIP 判「建筑」，靠人脸检测（置信度 ≥0.8）覆盖成「人像」。
  若人脸面积 < 0.2% 或侧脸则会漏。

## 6. 中文查询怎么修好的（改代码前必读）

原始状态：中文查询几乎不可用。逐一排查后的实测数据：

| 策略 | 与英文基准 top10 重合 |
|---|---|
| 纯中文 `猫` | 1% |
| 中英混合 `猫 cat` | 31% |
| **纯英文（词典替换）`cat`** | **85%** |

关键结论是**中文必须整个丢掉**，不是"补充"：
- `猫 cat` → 60%
- `猫在草地上 cat grass` → 20%

因为 CLIP 的 byte-level BPE 把每个汉字切成 3 字节 token，中文一多就把英文淹了。

所以 `services/zh_lexicon.py` 做的是**替换**：按长词优先把中文键换成英文，
停用词（的/在/和…）直接丢弃。命中率低于 34% 时退回原文（至少不比原来差）。

实测效果：

```
水下礁石     → underwater rock              top1 = 礁石照
中式古建筑   → chinese temple architecture   top1 = 古塔
日落         → sunset                        top1 = 日落
缆车         → cable car                     top1 = 缆车
江边风景     → riverside landscape           top1 = 河道
花卉特写     → flowers close-up              top1 = 花卉
```

代价：词表没收录的词会丢。UI 上会显示"词典未覆盖"，让用户知道为什么结果不对。

**为什么不用翻译模型**：opus-mt-zh-en 一类要 +300MB 模型、+200ms/查询，而摄影查询
词汇高度集中，150 条词表就能覆盖绝大多数场景。零下载、零延迟。

## 7. 实现里的三个坑（改代码前必读）

**① 必须乘 `logit_scale`**

CLIP 文本嵌入聚在窄锥内——「a photo of a bird」和「a photo of food」余弦 **0.935**，
真实类间差异只有 0.19~0.25。直接 `probs = sim / sim.sum()` 会把所有概率压到 `1/C`
附近，看起来像"模型没训练"。必须：

```python
logits = 100.0 * cos_sim      # logit_scale = ln(100)，训练学出来的温度
```

**② 一张图只解码一次**

`cv2.imread` 给检测解一次、`PIL.open` 给 CLIP 又解一次，24MP 的 JPEG 解码成本翻倍
（实测 96ms/张 → 240ms/张）。正确做法是一次解码成 PIL，转 numpy 给 OpenCV 检测，
同一张图再送 CLIP。

**③ 人脸置信度是比面积更好的判据**

实测真人脸置信度 0.848~0.902，假阳性（猫脸、建筑纹理误检）只有 0.594~0.651。
所以 `score >= 0.80 && 面积比 >= 0.002` 能干净切开，比单纯用面积阈值可靠得多。

## 9. 类别词表怎么改

`backend/services/fastvec.py` 的 `CLASSES` 是这套方案真正的"参数"——加类不增加推理成本
（只是一次矩阵乘多一列），但**每条锚描述越具体，精度越高**。

实测把 `"a photo of a bird"` 换成 `"a close-up photo of a bird with feathers and beak"` 之后：
中式宝塔照从「鸟类 0.66」变「建筑 0.72」，跑步照从「鸟类 0.43」变「人像 0.56」。

改完需要重建索引（`fastvec.db` 里的 `cat` 列是建索引时写死的）。

## 10. 复现与测试

### 10.1 分类与检索基准

```bash
# 只看结果（人工核对）
python scripts/bench-fast-classify.py D:/pics --limit 30

# 有标注时算准确率（CSV 两列：文件名,正确类别）
python scripts/bench-fast-classify.py D:/pics --limit 30 --labels labels.csv

# 中文检索 vs 英文基准的 top-10 重合率
python scripts/bench-fast-classify.py D:/pics --bench-search
```

脚本不写库、不改索引，纯读图跑一遍。分类准确率的分母是**有标注的行数**，不是图片总数。
检索重合率衡量的是「中文查询能否复现英文查询的结果」，**不等于检索相关性准确率**。

### 10.2 回归测试

```bash
pip install pytest
pytest backend/tests -v
```

16 个用例，覆盖 review 指出的全部问题：

| 用例 | 锁住的行为 |
|---|---|
| `test_verify_rejects_truncated` / `_oversize` | 下载校验不接受截断或超长文件 |
| `test_download_overwrites_on_200` | 服务器忽略 Range 时覆盖写，不追加 |
| `test_file_specs_are_exact` | 脚本里的期望值必须是 HF 官方的真实大小与 sha256 |
| `test_index_error_resets_running` | 初始化异常后 `running` 必须复位（否则永久 409） |
| `test_bad_image_is_marked_error` | 解码失败记 error，不产出分类结果 |
| `test_bad_images_do_not_become_identical` | 多张坏图不会被当成同一组重复 |
| `test_analyzer_batch_guard_is_atomic` | `try_acquire_batch` 第二次必失败 |
| `test_analyze_batch_honours_preacquired` | `_preacquired=True` 不被误判成重复请求 |
| `test_search_response_contract` | 搜索返回 `items`，前端据此替换 `state.items` |
| `test_lexicon_*` | 扩展结果不含中文、未覆盖时回退、长词优先 |

测试**不需要真实模型**：模型加载与编码都被 monkeypatch 掉，没有 148MB 模型也能跑。

## 11. 未验证项（已知缺口）

诚实列出，避免误导：

- **打包体积**：`spec` 的条件排除逻辑只做了静态审查，**未实际构建两种产物对比体积**
- **Windows 安装包**：未在无模型 / 有模型两种配置下各打一次包验证运行时行为
- **高置信误判率**：30 张样本不足以分层评估，没做
- **前端「搜索后全选」**：只锁了 API 契约，浏览器内的实际交互需真机验证
- **降 LLM 调用量不是自动的**：需要人工选中低置信项并点「提交 LLM 复核」，
  不点就是纯本地分类、零 LLM 调用
